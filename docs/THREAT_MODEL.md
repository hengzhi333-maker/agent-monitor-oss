# Threat Model

## Scope

Agent Monitor is intended for one owner controlling their own workstation from
their own Android phone over Tailscale or a trusted LAN.

Out of scope:

- public multi-user hosting,
- anonymous access,
- direct public-internet exposure without a reverse proxy and additional
  controls,
- protecting against a fully compromised workstation or phone.

## Assets

- daemon bearer token,
- local agent conversations,
- uploaded workbench files and extracted text,
- workstation filesystem paths and project names,
- sub2api admin credentials or tokens,
- Codex/Claude command execution capability.

## Trust Assumptions

- The phone owner and workstation owner are the same person.
- The private network is trusted, preferably Tailscale.
- `daemon/config.json` and Android encrypted host storage remain private.
- Workbench allowed directories are intentionally chosen by the owner.

## Primary Risks and Mitigations

### Token Theft

Impact: attacker can call protected daemon APIs.

Mitigations:

- long random token generated by `npm run gen-token`,
- optional multi-token configuration for staged rotation and separate devices,
- token rotation endpoint,
- failed-auth rate limiting for REST and WebSocket upgrades,
- git ignores real config files,
- Android stores host config through encrypted storage.

### Unauthorized Remote Device

Impact: attacker on the same network can control the workbench if they also get
the token.

Mitigations:

- `remoteControl.allowedRemoteAddresses` exact IP/CIDR allowlist,
- diagnostics and security center expose allowlist state,
- Tailscale/LAN deployment guidance.

### Remote Code Execution

Impact: the phone can start Codex/Claude Code on the workstation.

Mitigations:

- remote workbench disabled by default,
- `allowedCwds` limits working directories,
- dangerous permission mode disabled by default,
- agent commands use argument arrays instead of shell command strings.

### Upload and Local Path Leakage

Impact: uploaded files can contain secrets; local file paths may reveal user or
project names.

Mitigations:

- upload size and type allowlists,
- server-generated upload filenames,
- uploads stored outside static web roots,
- local image paths are not included in the natural-language prompt,
- optional snapshot `cwd` basename redaction,
- configurable Hermes status truncation,
- attachment TTL cleanup, explicit delete, and explicit cleanup endpoints,
- redaction masks common secrets, authorization headers, emails, and local user
  paths in history/audit views.

### Denial of Service

Impact: large requests or slow HTTP clients can consume daemon resources.

Mitigations:

- JSON body size limits,
- raw upload size limits,
- JSONL parsing cache has an LRU cap,
- repeated failed authentication attempts are rate limited per source,
- Node request/header/keep-alive timeouts,
- per-session attachment and output limits.

## Cleartext HTTP

The Android app allows cleartext HTTP because the expected daemon URLs are
private Tailscale/LAN addresses. Do not expose the daemon directly on the public
internet. Use HTTPS/WSS only when TLS is terminated by a trusted reverse proxy or
another trusted layer. The daemon can also serve HTTPS/WSS directly when
`tls.cert` and `tls.key` are configured.
